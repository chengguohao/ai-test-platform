# 被测系统接入与平台操作手册

> 适用人员：测试人员 / 维护 pytest 工程的人
> 配套版本：2026-08-31「被测系统解耦」改造后
> 一句话：平台负责生成/编排/报告，**被测系统只认项目里填的 gen_dir**；换系统不用改平台代码。

---

## 一、先搞懂两个概念（2 分钟）

| 概念 | 是什么 | 谁去动 |
|------|--------|--------|
| **pytest 框架工程**（pytest-bdd） | 测试脚本的执行宿主：pytest + Allure + 声明式 ApiCase 体系 | 平台固定依赖，不用换 |
| **被测系统**（如 SmartAdmin） | 被测的那套业务系统，在框架工程里是 `tests/api/{系统名}/` 一个子目录 | 新建项目时填 gen_dir 指向它 |

平台通过**扫描**被测系统子目录决定一切适配（fixture 清单、业务码表、marker、角色体系），全部自动，不写死任何系统名。

关键概念：
- **gen_dir**：项目配置里的「用例生成目录」，指到 `tests/api/{系统名}`，平台就在那里生成/执行用例。
- **marker**：用例标签。工程开了 `--strict-markers`，**标签必须先在 pyproject.toml 登记**，否则 pytest 直接报错跑不起来。
- **业务码表**（可选）：`support/fixtures/xx.py` 里的 `XX_CODES: dict`，用于断言业务失败信封；没有也能跑，自动降级为 `exists /msg` 断言。

## 二、接入一个新被测系统（搭建时一次性动作，约 10 分钟）

> 以下 1-3 步在 pytest 工程里，第 4 步在平台里，第 5 步验证。

### 第 1 步：建被测系统子目录 + conftest

在框架工程下创建：

```
pytest-bdd/tests/api/{系统名}/
    conftest.py        # 提供本系统 fixture
    {模块}/
        test_{模块}.py # 平台生成到这里
```

`conftest.py` 至少提供 `base_url`、`api_client` 两个 fixture（可复用 `support/` 公共件，参考现有 `tests/api/smartadmin/conftest.py`）。fixture 不用写全，平台会自动扫描继承链上真实存在的 fixture 并喂给 AI，AI 不会瞎编。

### 第 2 步：登记业务 marker（必须，一行）

打开框架工程根目录 `pyproject.toml`，在 `markers` 列表追加：

```toml
markers = [
    # ……已存在的……
    "oss: Oss 项目",          # ← 新系统加这一行，名字随便起，跟子目录同名最省事
]
```

**不登记会怎样**：AI 生成的用例会挂业务标签（如 `@pytest.mark.oss`），而 `--strict-markers` 要求标签必须先登记，没登记 → pytest 收集阶段直接报错，**整个测试一个都跑不了**。

### 第 3 步（可选）：提供业务码表

被测系统有"业务失败信封"（如 code≠0 表示失败）时，推荐在工程里建：

```
pytest-bdd/support/fixtures/oss.py
```

内容示例：

```python
OSS_CODES: dict = {
    "forbidden": 40301,       # 越权
    "not_login": 40101,       # 未登录
}
```

不建也完全能跑：AI 会自动改用"校验失败信封存在"的断言，只是反例断言粒度略粗。

### 第 4 步：平台新建项目，填 gen_dir

工作台首页 → 新建项目 → 「被测系统与执行引擎」区：

| 字段 | 填什么 |
|------|--------|
| pytest 项目目录 | 框架工程绝对路径（默认已填好，不用动） |
| 用例生成目录（gen_dir） | `tests/api/{系统名}`，**多系统并存时必填**；整个工程只有一套系统时可以留空自动识别 |

被测系统地址 / 账号 / 密码照常填（只影响执行时的登录和连通，与生成无关）。

### 第 5 步：验证

1. 打开该项目工作台，逐阶段走完「需求上传 → 接口文档 → 生成用例 → 自动化生成」；
2. 自动化生成日志顶部会打印：`被测系统=Oss, 可用 fixture N 个`；
3. 检查生成的 `test_{模块}.py` 文件头挂了 `@pytest.mark.api`（有业务 marker 则同时挂 `@pytest.mark.oss`），import 的是你工程的真实模块；
4. 被测系统服务启动后点「执行」，Allure 报告正常生成即接入成功。

## 三、日常使用（接入后，每个项目每轮都这么做）

工作台 5 个阶段，状态全自动推进，人只保留两个动作：**传文档**、**评审用例**。

1. **需求上传**：上传需求文档（.docx/.md，含图片会自动识图规范化）。
2. **接口文档**：上传接口文档（推荐 JSON 格式模板）。
3. **生成用例**：AI 自动生成「业务功能用例」和「接口测试用例」，逐条人工核对，点「评审通过」。→ 未评审通过不会进入下一步（卡片会显示"待评审"）。
4. **自动化生成**：AI 按接口文档把已评审用例转成 pytest 脚本，可导出 XMind / Excel。
5. **执行报告**：被测系统启动后一键执行，自动出 Allure 报告，失败会走 AI 修复闭环。

> 登录被测系统账号（admin/123456 等）在**项目编辑**里维护，不是平台登录。

## 四、常见问题排查

| 现象 | 原因 | 处理 |
|------|------|------|
| 执行报 `no tests ran` / 报告为空 | 用例挂的业务 marker 与执行过滤不一致 | 确认 pyproject.toml 登记了该 marker，且用例文件头挂对应标签；或让 exec 不按 marker 过滤（gen_dir 指向无 marker 的新系统时自动如此） |
| pytest 收集阶段报 unrecognized marker 错误 | `--strict-markers` 下用了未登记标签 | 把该 marker 加进 pyproject.toml（见第二节第 2 步） |
| 报 `fixture not found` | 用例用了系统子目录 conftest 继承链上没有的 fixture | 检查 conftest 是否提供该 fixture；平台只按"文件所在目录到项目根"的继承链收集，不会混入兄弟系统子目录的 fixture |
| 反例断言报业务失败但拿不到业务码 | 业务码表未提供或键不对 | 提供 `support/fixtures/{系统}.py` 的 `XX_CODES: dict`；没有时 AI 会退化为"失败信封 exists"断言，属正常降级 |
| 生成日志显示 `被测系统=Smartadmin` 这类首字母大写名字 | 展示名自动取子目录名 | 想显示为「SmartAdmin」可把子目录命名成 `smartadmin`；仅影响 Allure 标题展示 |
