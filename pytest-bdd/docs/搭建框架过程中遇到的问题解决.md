## 1. PyCharm 左侧要显示每条接口

- **问题**：在 PyCharm 中运行 feature 和 api 时，左侧面板只显示一个测试结果节点，希望能把每个接口、每个步骤都展示出来，方便批量跑时看单个接口/步骤的执行情况。
- **背景**：早期实现只做了"右侧 Test Output 打印接口详情块"，用户澄清要的是**左侧测试树**里每条接口一个节点。
- **解决**：
  1. 最初用 `pytest-subtests` 插件在 `run_case` 内包 subtest，PyCharm 2020+ 理论上可展开；
  2. 实测 PyCharm 对 subtests 的树形展示依赖 IDE 版本，不稳定；
  3. 最终统一改用 **`@pytest.mark.parametrize` 展开**：每个 `ApiCase` / `FlowStep` 展开成一条独立 pytest 节点，PyCharm 原生支持，可单独看结果 / 单跑。
- **状态**：✅ 已解决（parametrize 展开为唯一标准）
- **涉及文件**：`tests/api/smartadmin/test_enterprise_crud.py`、`tests/api/smartadmin/test_role_access_flow.py`、`docs/框架执行流程说明.md`

## 5. 断言怎么没写在 ApiCase 里？（信封守卫）

- **问题**：很多 ApiCase 里 `assertions=[]`，没看到断言。
- **解决**：这是框架的**信封守卫**机制——当 `biz_auto=True`（默认）且响应是 SmartAdmin 信封（含 `ok` 字段）且断言里没显式写 `/ok`/`/code` 时，`run_case` 自动在断言列表前插入 `Assertion.biz_ok()`（`ok=true` 且 `code=0`）。`assertions=[]` 表示"用默认业务成功断言"，只有字段级校验才需显式写。
- **状态**：✅ 已解决（机制说明）
- **涉及文件**：`support/api_case.py::run_case`、`Assertion.biz_ok()`

---

## 6. 异常场景能在 assertions 里现加断言吗？

- **问题**：正例返回值基本一致可以用隐式 biz_ok，但异常场景千奇百怪，能否在 assertions 里现加？例如 `Assertion(expected='查询失败', field="/data/msg", reason="查询失败")`，实际接口返回了"查询失败"，断言结果会显示成功吗？
- **解决**：**实测验证**了 4 种写法：
  - 没关 `biz_auto` → 信封守卫误加 biz_ok，异常 ok=false 误报失败；
  - `biz_auto=False` + `field="/msg"` → **断言成功显示"断言结果：成功"**（正确写法）；
  - `biz_auto=False` + `field="/data/msg"` → 失败（msg 在**顶层** `/msg`，不在 data 里）；
  - `biz_auto=False` + `/msg` 但值不匹配 → 失败。
- **结论**：异常场景可以在 assertions 现加断言，但**必须 `biz_auto=False`** + **`field="/msg"`（顶层）** + **expected 与实际一致**。
- **状态**：✅ 已解决（实测 4 种写法）
- **涉及文件**：`support/api_case.py`

## 8. 断言数据改为可读 {code, msg}，去掉 ok

- **问题**：这样显示太难阅读。biz_ok 的断言数据改为 `{"code": 0, "msg": "操作成功"}`，`ok` 不要了；异常场景也改为这种格式。例如 `msg exists True` 应显示为 `{"code": 30005, "msg": "对不起，您没有权限访问此内容哦~"}`。日志应更考虑阅读，而不是程序化。
- **解决**：在 `run_case` 里组装人可读的"断言数据"：
  - `code` 取断言期望值（biz_ok→0 / biz_fail→业务码 / 用户显式 code），**`ok` 不展示**；
  - `msg` 优先取断言期望值；未显式断言（或仅 `exists`）时取**实际返回**的 msg；
  - 通过 `record_assertions(data=...)` 传给 `render_assertion` 展示。
- **效果**（实测）：正例 `{"code": 0, "msg": "操作成功"}`；重名 `{"code": 30001, "msg": "企业名称重复"}`；越权 `{"code": 30005, "msg": "对不起，您没有权限访问此内容哦~"}`。
- **状态**：✅ 已解决
- **涉及文件**：`support/api_case.py`、`support/clients/api_client.py`

## 9. "管理员-分页反查id" 两条 Assertion 的作用

- **问题**：`管理员-分页反查id` 下的 assertions 里有两条 Assertion，这个作用是什么？
- **解决**：
  - ① `Assertion(expected=1, op="gte", field="/data/total")`：校验分页返回 `total >= 1`，证明刚创建的企业**能被按名称反查到**；
  - ② `Assertion(expected=ENT_NAME, op="eq", field="/data/list[0]/enterpriseName")`：校验列表第一条企业名**恰好等于**刚创建的企业名，排除重名/脏数据干扰。
  - 两者共同保证 `save` 取出的 `enterpriseId`（存为 `ent_id`）就是刚创建的那家，后续步骤用 `${ent_id}` 查/改/删的都是同一家企业。
- **状态**：✅ 已解决（说明）

## 10. 为什么"管理员-分页反查id"断言数据丢 code？

- **问题**：为什么只有这条 ApiCase 打印的日志里，断言数据里面没有 code？
- **解决**：排查发现该 case 被**误加了 `biz_auto=False`**。`biz_auto=False` 会关闭信封守卫，不再自动追加 `biz_ok`，断言列表里没有 `/code` 断言，因此"断言数据"组装时拿不到 `code`，只剩实际返回的 `msg`（`{"msg": "操作成功"}`）。
- **修复**：删除误加的 `biz_auto=False`（该条是正例，应让信封守卫自动校验 `ok=true`/`code=0`），恢复 `{"code": 0, "msg": "操作成功"}`。
- **沉淀**：项目记忆新增警告——**`biz_auto=False` 只用于异常/越权用例，正例（成功）用例绝不能设**。
- **状态**：✅ 已修复
- **涉及文件**：`tests/api/smartadmin/test_role_access_flow.py`

---

## 11. reason 的作用是描述吗？

- **问题**：`Assertion` 的 `reason` 参数作用就是描述吗？
- **解决**：不只是描述。`reason` 是**断言失败时的人读失败原因说明**：
  - 不影响断言通过/失败（成败只看 `expected/op/field` 与实际值比对）；
  - 断言成功时完全用不到；失败时展示在日志断言块（"断言失败原因：..."）与 `failure_summary`（"原因=..."）；
  - 不写时框架自动生成 `预期 X，实际值为 Y`；
  - 建议写**业务含义**（为什么要有这个断言），而非重复 desc。
- **状态**：✅ 已解决（说明）

## 12. 日志里为什么有 \xb7

- **问题**：`订单全链路·步骤1·创建订单`，为啥日志有个 `xb7`？
- **解决**：pytest 对参数化 id 里的中圆点 `·`（U+00B7）会转义成 `\xb7`（latin-1 单字节字符走 `\xXX` 两位转义）。原 `_unescape_node_id` 只处理了四位的 `\uXXXX`，增强正则同时支持 `\xXX`（两位）与 `\uXXXX`（四位），节点名恢复正常中文显示。
- **状态**：✅ 已解决
- **涉及文件**：`tests/conftest.py::_unescape_node_id`

## 17. 多角色执行同一接口结果不同，框架如何设计（越权/鉴权）

- **问题**：自动化中还有鉴权，不同角色执行同一接口结果是不同的，比如平行越权和水平越权：管理员可新增/修改等全部权限，填报员只能查询；流程中管理员新增 → 填报员修改 → 审核员审核 → 打回 → 填报员重提 → 管理员报送/最终操作。现有框架怎么设计？
- **解决**：多角色 RBAC 设计落地：
  - 角色会话池：`.env SA_ROLES_JSON` 配置 admin/reporter/auditor，每角色独立 `ApiClient` + 独立 token，`role_registry[role]` 懒登录；
  - 用例形态：`FlowStep(role, case)` + **parametrize 展开**（后固化），module 级 ctx 串联 ent_id；
  - 越权断言：探测 `SA_CODES["forbidden"]`，低权限角色调高权限操作断言 `biz_fail(forbidden)`；
  - 演示文件：`tests/api/smartadmin/test_role_access_flow.py` + `role_access_flow.feature`。
- **状态**：✅ 已解决
- **涉及文件**：`.env`、`support/fixtures/smartadmin.py`、`tests/api/smartadmin/test_role_access_flow.py`、`tools/sql/create_rbac_accounts.sql`

# 框架搭建过程中的其他 Bug 修复记录

## 21. feature 文件报 "Multiple features are not allowed"

- **问题**：`pytest_bdd.exceptions.FeatureError: Multiple features are not allowed in a single feature file`。
- **解决**：feature 文件使用 `功能:`（Feature 关键字）时存在缩进/格式问题，修正关键字与缩进后正常。
- **状态**：✅ 已修复

## 22. FlowCase 扁平化后 NameError: api_client is not defined

- **问题**：将 FlowCase 步骤扁平化后，测试函数报 `NameError: name 'api_client' is not defined`。
- **解决**：测试函数签名补齐 `api_client`、`ctx` 等参数（pytest 按参数名注入 fixture）。
- **状态**：✅ 已修复

## 23. 登录失败"未登录或登录失效"（30007）

- **问题**：请求报 `未登录或登录失效`（业务码 30007）。
- **解决**：SmartAdmin 鉴权走 `Authorization: Bearer <token>` 请求头，而非 cookie。`ApiClient` 注入 token 到请求头，`sa_login` 解析并设置 token。
- **状态**：✅ 已修复

## 24. 自动重登后 Authorization 头丢失

- **问题**：会话过期自动重登后，重发的请求仍没有带上新 token（命中 30007）。
- **解决**：`ApiClient` 自动重登逻辑中，重发原请求前用新 token 重建 `Authorization` 头，避免重发裸请求。
- **状态**：✅ 已修复
- **涉及文件**：`support/clients/api_client.py`

## 25. BDD 步骤定义未找到

- **问题**：BDD 场景执行时提示步骤定义未找到。
- **解决**：步骤正则与 feature 文本不匹配（模式中多了一个空格），调整正则后匹配成功。
- **状态**：✅ 已修复
