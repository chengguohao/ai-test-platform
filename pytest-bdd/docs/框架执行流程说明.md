# pytest-bdd 框架执行流程说明（新人培训版）

> 面向第一次接手本项目的测试同学。目标是 30 分钟内看懂：
> **代码是怎么跑起来的、谁引用谁、数据怎么流转、左侧测试节点名是什么意思。**

---

## 1. 一句话总览

本框架是「**声明式用例 + 引擎执行**」模式：

- 你不用写一串 `if/else` 的测试代码；
- 而是像**填表**一样声明接口（`ApiCase`：方法 / 路径 / 入参 / 断言 / 要保存的动态参数）；
- 再把声明交给统一的**执行引擎** `run_case()` —— 它负责发请求、走「信封守卫」、逐条断言、把中间数据 `save` 进上下文；
- 后续用例通过 `${变量}` 占位符引用上下文里的值，形成**数据串联**。

## 3. 执行流程（5 个阶段）

```
① 运行命令
  pytest tests/api/smartadmin -m smartadmin --alluredir allure-results
      │
      ▼
② 收集阶段（pytest 收集测试，只发现不执行）
  - 加载子目录 conftest：
      · SA_PASSWORD 为空 → 给所有 smartadmin 标记用例打 SKIP（见 §6）
      · 定义被测系统专属 fixture（api_client → SmartAdmin 登录会话）
  - parametrize 把 CASES 列表展开成 8 个独立测试节点
      │
      ▼
③ 执行前 fixture 装配（pytest 按「参数名」自动注入）
  def test_enterprise_crud_case(api_client, ctx, cleanup_registry, case)
                                │          │                │          │
                                ▼          ▼                ▼          ▼
                         登录会话(session)│   module级上下文 清理注册表  当前这条用例
                         先走 sa_login()   │                 │
                                          ▼                 ▼
                                   bind替换${var}   封装请求并缓存到 history
      │
      ▼
④ run_case() 引擎内部 5 步
  bind 替换 ${占位符} → 发请求（自动带 cookie）→ 信封守卫（自动加 biz_ok）
  → 逐条断言 + save 动态参数回 ctx → **parametrize 展开成独立节点（PyCharm 左侧每条接口一节点）**
      │
      ▼
⑤ 收尾
  - 根 conftest 的 pytest_runtest_makereport 钩子按"增量"打印「接口块 + 断言块」到 Test Output
    （subtest 报告时只打"本次新增"那一段，父 test 报告时再补齐最后一段，去重）
  - api_client 关闭 → 触发 CleanupRegistry.flush() 统一删除测试数据
  - --alluredir 落盘 allure-results → allure generate 出 HTML 报告
```

## 4. A 怎么引用 B（两种引用方式）

### 4.1 静态 import（编译期，写死在文件头部）

`test_enterprise_crud.py` 顶部：

```python
from support.api_case import ApiCase, Assertion, run_case
from support.fixtures.context import ScenarioContext
from support.fixtures.smartadmin import SA_CODES   # 探测到的业务失败码
```

这是「文件级：谁能调用谁」。import 链是：

- `test_*.py` → `support/api_case.py`（引擎）
- `test_*.py` → `support/fixtures/context.py`（ctx 类型，仅做类型注解）
- `test_*.py` → `support/fixtures/smartadmin.py`（读 SA_CODES，动态注入 biz_fail 断言）
- `support/api_case.py` → `support/fixtures/context.py`（用到 ScenarioContext）
- `support/fixtures/smartadmin.py` → `support/clients/api_client.py`（实例化 ApiClient）

### 4.2 运行时注入（pytest 魔法，最重要）

测试函数签名里的**参数名**就是声明：「我要求 pytest 给我一个叫这名字的东西」：

```python
def test_enterprise_crud_case(api_client, ctx, cleanup_registry, case):
```

pytest 在 conftest 里按**同名**找 fixture（就近规则：子目录 conftest 生效）：

- 根目录 `tests/conftest.py` 只保留全局钩子，**不定义**任何被测系统 fixture；
- `tests/api|acceptance/smartadmin/conftest.py` 定义 `api_client`（指向 SmartAdmin + 自动登录）、`ctx`、`cleanup_registry` 等全部被测相关 fixture，默认就在这两个目录内生效；
- 后续若新增第二个被测系统（如 A 项目 / B 项目），各自开一个子目录 + 子目录 conftest 定义同名 fixture，互不干扰 → **这就是模块隔离的原理**。

> 规避经验：两个子目录 conftest 不重复写登录/清理逻辑，而是共同调用
> `support/fixtures/smartadmin.py` 里的 `make_sa_fixture_functions()` 工厂，
> 拿到【未装饰】的原生函数后再各自 `pytest.fixture(...)` 装饰一次（避免"fixture applied more than once"报错）。

## 5. 数据是怎么流转关联的（3 个载体，3 种生命周期）

以「企业 CRUD」9 条用例为例：

```
① 登录                      ② 创建 C1             ③ 查/改/删 D1/U1/X1      ④ 收尾
POST /login                → POST /create        → GET /get/${ent_id}    → flush()
satoken 写进 cookie jar    → save /data/id       → POST /update(id=)     → 逐条
   │                         → ctx.ent_id          GET /delete/${ent_id}   GET /delete/{id}
   ▼                          │                      │                       │
[httpx cookie jar]   [ScenarioContext (ctx)]  [bind() 运行时替换]   [CleanupRegistry]
会话级，全程自动携带       module级，跨用例串值       发请求前替换占位符      session级，统一删除
```

| 载体 | 生命周期 | 谁来写 | 谁来读 | 作用 |
|---|---|---|---|---|
| `httpx.Client` cookie jar | session | `sa_login()`（登录响应 Set-Cookie） | 所有 `request()` | Sa-Token 会话，无需手动传 token |
| `ScenarioContext` (ctx) | L2: module；L3: 每场景 | `case.save={"/data/id": "ent_id"}` | 后续 case 的 `path/body` 里 `${ent_id}` → `ctx.bind()` | 上一步返回值作为下一步入参 |
| `CleanupRegistry` | session | 测试中 `register_delete(path, id)` | 结束 `flush()` | 防数据污染 |

**关键代码位置**：
- save 定义：`tests/api/smartadmin/test_enterprise_crud.py` 第 63 行 `save={"/data/id": "ent_id"}`
- bind 替换：`support/fixtures/context.py` 的 `bind()`（支持 str / dict / list 递归替换）
- run_case 里的执行顺序（`support/api_case.py`）：发请求 → 信封守卫 → 断言 → save → 返回结果

## 6. 节点信息解读（PyCharm 左侧面板）

节点全名 = `目录::文件::函数[参数id]`。两类典型节点：

| 类型 | 节点示例 | 拆解 |
|---|---|---|
| L2 接口用例 | `test_enterprise_crud_case[企业-C1-创建成功]` | 函数名是 parametrize 模板；`[...]` 是 `CASE.name`。8 条 CASE = 8 个独立节点，可单跑 / 单看结果 |
| L3 BDD 场景 | `test_创建企业后按名称关键字分页查询可命中[SA_BDD_企业A_${ts_token}-王大锤-...]` | 函数名 = 场景名；`[...]` = 场景大纲 Examples 的一行（2 组例子 = 2 个节点）；`${ts_token}` 是**运行期**才由 ctx 替换的唯一化占位符 |

> 同理，如果把业务链用 parametrize 平铺成"流程名·步骤N·步骤名"的 id，也能让链条上每个接口在左侧显示成独立节点，方便单看每一步。

节点状态：**绿 = 通过 / S = 跳过 / R = 失败**。跳过原因悬停可见（如"未配置 SA_PASSWORD"）。

### 接口执行明细打印（每个 API 执行脚本标配，必须有）

每个用例执行结束后，控制台（PyCharm 运行面板）**自动打印本次用例发起的每条接口明细**，由根目录
`tests/conftest.py` 的 `pytest_runtest_makereport` 全局钩子统一提供，**不需要每个脚本自己写打印代码**，
新增的任何 API/BDD/多角色脚本都会自动继承。每条接口输出如下（示例为越权被拒场景）：

```
======================================================
接口名称 : [auditor]修改企业
请求方法 : POST
请求地址 : http://127.0.0.1:1024/oa/enterprise/update
接口状态 : 成功  (200)   耗时 0.007 秒
body   : {"enterpriseName": "RBAC_BDD_A_...", ..., "enterpriseId": 276}
接口返回数据 ：{"code": 30005, "msg": "对不起，您没有权限访问此内容哦~", "ok": false}
断言结果 ：成功
```

- 覆盖范围：普通 L2 接口用例、L3 BDD 场景、跨角色流程（角色会话池的请求也会聚合打印）；
  一次用例多步 → 按调用顺序逐条打印，最后附 `[用例结论] 共 N 次接口调用`。
- 开关：默认开启。需要关闭时设环境变量 `API_DEBUG=0`（或 `1` 强制开启）。
- 每个用例对应独立基准：`pytest_runtest_setup` 记录各客户端的起始历史，只打印本次用例新增的请求，
  不会把登录/探测/清理的请求混进来。

### 常见疑问

- **为什么节点名里出现 `\xb7` 之类的乱码**：pytest 对参数化 id 里的非 ASCII 字符（如 `·` U+00B7）做了 `\xXX` 转义。根目录 `tests/conftest.py` 的 `_unescape_node_id` 钩子在收集阶段统一还原（`\uXXXX` 和 `\xXX` 两种都处理）。若乱码复现，先检查该函数。
- **为什么有的用例是 SKIP 而不是失败**：`.env` 里 `SA_PASSWORD` 留空时，collection 阶段会给所有 `smartadmin` 标记的用例打 SKIP，这是**有意设计**——没密码不联网、不产生脏数据。

## 7. 信封守卫（SmartAdmin 专属魔法点，务必理解）

`run_case()` 里唯一一处**隐式行为**，同时满足 3 个条件才会触发"自动追加 `biz_ok` 断言（ok=true 且 code=0）"：

1. `case.biz_auto = True`（默认）；
2. 响应是 dict 且含 `ok` 键（即 SmartAdmin 统一信封 `{ok, code, msg, data, ...}`）；
3. 用例自己的断言里**没有**显式写过 `ok` / `code` 字段断言。

这就是为什么**普通 REST 接口（响应不带 `ok` 字段时）不会被被动判定为业务成功**，而 SmartAdmin 用例又不用每条手写成功断言——守卫只在「信封形状」成立时才自动生效。

- 失败用例请显式 `biz_auto=False` + `Assertion.biz_fail(code=业务码)`；
- 业务码（重名 / 删除不存在 / 未登录）由 session 级 autouse fixture **故意触发失败场景探测**得到，存在 `SA_CODES` 中（见 `support/fixtures/smartadmin.py`）。

## 10. 多角色 & RBAC 测试（跨角色业务流）

### 10.1 为什么需要

不同角色执行同一接口结果不同：管理员可增删改查/报送，填报员只能查询+改自己数据，
审核员只读审核——这就是 RBAC 权限矩阵与**越权**（垂直/水平）测试的土壤；
模块流程（新增→填报→审核→打回→重提→报送）则是**跨角色协同**链路。

### 10.2 核心机制：每角色独立会话

- 每个角色 = 独立登录账号 + 独立 token + 独立 `ApiClient`（后端按账号生成互不相同的 token）。
- 登录日志按角色打印：`[SmartAdmin 登录成功] 角色=reporter 用户=reporter01 ... token=<独立值>`。
- 角色账号配置在 `.env SA_ROLES_JSON`；`load_sa_roles()` 解析、`get_role_client(role)` 懒登录缓存（`SA_ROLE_CLIENTS` 池）。

### 10.3 用例模型：FlowStep 步骤 + parametrize 展开（推荐，PyCharm 每条接口一节点）

`test_role_access_flow.py` 与 `test_enterprise_crud.py` 同款「parametrize 展开 + module 级 ctx 串联」：
- `FlowStep(role, case)` 声明每一步的执行身份；
- `@pytest.mark.parametrize("step", FLOW_STEPS, ids=lambda s: s.case.name)` 把流程**展开成 N 条独立 pytest 节点**，PyCharm 左侧每条接口一节点（原生支持，与 CRUD 用例体验一致）；
- 节点内 `client = role_registry[step.role]` 取该角色独立会话，`run_case(client, ctx, step.case)` 执行；`save/${var}` 跨步骤通过 module 级 `ctx` 串联。

```python
from support.api_case import ApiCase, Assertion, FlowStep, run_case

FLOW_STEPS: list[FlowStep] = [
    FlowStep("admin",    ApiCase(name="管理员-创建企业", ...)),
    FlowStep("admin",    ApiCase(name="管理员-分页反查id", save={"/data/list[0]/enterpriseId": "ent_id"}, ...)),
    FlowStep("reporter", ApiCase(name="填报员-修改企业(填报)", body=dict(..., enterpriseId="${ent_id}"), ...)),
    FlowStep("auditor",  ApiCase(name="审核员-越权修改(应拒绝)", biz_auto=False, assertions=[])),  # 越权
    ...
]

@pytest.mark.parametrize("step", FLOW_STEPS, ids=lambda s: s.case.name)
def test_enterprise_role_access_step(role_registry, ctx, cleanup_registry, step: FlowStep):
    client = role_registry[step.role]          # 懒登录独立会话
    result = run_case(client, ctx, step.case)  # 单步执行
    assert result.passed, f"[{step.role}] {step.case.name}: {result.failure_summary}"
```

- 批量跑时按声明顺序执行完整业务流；每个步骤节点可单独看结果。
- 单步/旧用例：`run_case(api_client, ctx, case)` 与 `run_flow` 签名不变，零影响。
- 若要用「单个 test 函数跑完整 FlowCase」，`support/api_case.py` 仍保留 `run_flow(api_client, ctx, flow)` / `run_flow_as(role_clients, ctx, flow)` 供选用（此时左侧只有 1 个节点，步级粒度靠 Allure/日志）。

### 10.4 越权断言语义

- **越权码探测**：session 启动时用低权限角色（优先 reporter）调用管理员专属删除操作，探测 `SA_CODES["forbidden"]`（探测不到 → 越权断言用例 SKIP）。
- 垂直越权（低权限调高权限）示例：审核员尝试修改企业 → `Assertion.biz_fail(code=SA_CODES["forbidden"])`。
- 水平越权（平行越权，他人资源）：框架预留 `SA_CODES["forbidden"]` + 角色会话，后续按「以 B 的 token 访问 A 的资源 id」扩展即可。

### 10.5 BDD 写法

```gherkin
场景大纲: 管理员-填报员-审核员 跨角色企业流程
  当 以 "admin" 身份调用 企业 创建接口，企业名="<企业名>"
  那么 业务信封 返回成功
  当 以 "auditor" 身份调用 企业 修改接口，企业名="<企业名>"
  那么 业务信封 返回失败（越权无权限）
  例子:
    | 企业名                 |
    | RBAC_BDD_A_${ts_token} |
```

通用步骤「以 {role} 身份调用 企业 {op} 接口」在 `tests/acceptance/smartadmin/steps/sa_common_steps.py`，
内部经 `role_registry[role]` 取会话，结果写入 `ctx.role_last_env` 供 then 断言。

### 10.6 账号缺失时的降级

`@pytest.mark.requires_role("reporter")`：collection 阶段检查 `SA_ROLES_JSON`，
未配置该角色 → 用例自动 SKIP。未配置任何角色时只跑纯 admin 用例（旧 15 条），不影响。

## 11. 接口执行明细打印（每个 API 执行脚本标配，必须有）

**目标**：PyCharm 左侧测试树**每条接口显示为一个独立节点**；右侧 Test Output 打印每条接口的详细块。

### 11.1 左侧：每条接口一个节点（parametrize 展开，**强制**）

**项目规范：所有 API 接口脚本必须用 `@pytest.mark.parametrize` 展开**（每个 `ApiCase` / `FlowStep` 一条独立 pytest 节点），这是 PyCharm 测试树原生支持、最可靠的方式，也是 AI 生成用例的唯一标准写法。
PyCharm 测试树只识别 pytest 收集到的节点，不会解析 print 日志。
- `test_enterprise_crud.py`：`@pytest.mark.parametrize("case", CASES, ids=lambda c: c.name)` → 每条 ApiCase 一个节点；
- `test_role_access_flow.py`：`@pytest.mark.parametrize("step", FLOW_STEPS, ids=lambda s: s.case.name)` → 每个 FlowStep 一个节点，`role_registry[step.role]` 按角色执行。

PyCharm 左侧显示（每条接口一节点，可单独看结果 / 单跑）：

### 11.2 右侧：Test Output 增量打印

由 `tests/conftest.py` 的 `pytest_runtest_makereport` 钩子 + `ApiClient.history` 记录实现：
- 每条 `request()` 调完后，渲染器输出 `接口名称/方法/地址/状态/耗时/请求/返回/断言` 块；
- 每个 pytest 节点只打"该节点新增"的请求段（以 setup 时记录的历史长度为基准），不重复；
- 结论行打印 `[用例结论] 节点名 → 成功/失败 （共 N 次接口调用）`。

关闭方式：`API_DEBUG=0` 环境变量。
